Вы подключились к сопровождению сервиса скрининга резюме. Ниже дано краткое описание текущей реализации.

За 10–15 минут:

2. Разберите один аварийный сценарий, который выберет интервьюер: последствия, восстановление и предотвращение повторения.

## Текущая реализация

### Получение резюме

- Рекрутер вручную загружает PDF, DOCX или TXT либо запускает импорт из hh.ru/rabota.by.
- Cron, webhook и регулярной фоновой синхронизации с площадками нет.
- Исходный файл сохраняется в Docker volume, извлечённый текст и метаданные — в PostgreSQL.
- Для PostgreSQL и файлового volume используются отдельные процедуры backup/restore.

### Скрининг

- Для запуска создаётся запись `screening_job` в PostgreSQL.
- Выполнение стартует через FastAPI `BackgroundTasks`.
- Одновременно обрабатываются не более трёх резюме; ограничение реализовано через `asyncio.Semaphore`.
- UI запрашивает состояния job примерно раз в три секунды.
- После рестарта `pending` запускаются снова, а незавершённые `processing` переводятся в `failed`.
- Одинаковые резюме с одинаковыми настройками дедуплицируются по хешу контекста.
- Сейчас backend работает в одном процессе. Семафоры и лимитеры хранят состояние в памяти процесса.

### Внешние сервисы

- hh.ru и rabota.by подключаются по OAuth; access/refresh tokens хранятся в PostgreSQL.
- У HTTP-запросов к площадкам есть timeout, но нет автоматических retry/backoff, в том числе после `429`.
- Обход списков ограничен двадцатью страницами.
- OAuth-вызовы ограничивает in-memory лимитер по IP.
- Для LLM предусмотрены основной и резервный endpoint, до трёх попыток с exponential backoff.
- Timeout одного LLM-запроса — 240 секунд, всего скрининга — 1800 секунд.
- Одновременно выполняется не более двенадцати LLM-запросов; лимит хранится в памяти процесса.
- Модель возвращает структуру и оценки категорий, итоговый балл рассчитывает код.

### Миграции

- При старте backend `SQLAlchemy create_all()` создаёт отсутствующие таблицы.
- Затем самописный runner последовательно выполняет ещё не применённые Python-миграции и отмечает их в `applied_migrations`.
- При ошибке миграции backend не запускается.
- Автоматического `downgrade` нет.
